[2026-08-03] DECISION: Calendar reads move from AppleScript to EventKit (`bridge/eventkit/read-events.ts`); writes stay on AppleScript. | REASONING: Calendar.app's scripting dictionary has no concept of a recurring *occurrence* — a weekly meeting is one object whose `start date` is its first occurrence, so `every event whose start date ≥ windowStart` compared this week against a date months in the past and dropped the entire series. Every standing meeting on every calendar was invisible. EventKit's `predicateForEvents(withStart:end:calendars:)` expands series properly and supplies `occurrenceDate` (RECURRENCE-ID). Cost is a second TCC grant (Full Access to Calendars), accepted because the alternative — expanding RRULEs client-side — cannot see EXDATEs through AppleScript and would report cancelled occurrences as real. | CONTEXT: Found when MAISIE reported a clear Tuesday afternoon and Jack knew Hanover Food Truck Day was on it. A 7-day read returned 4 events; the correct answer was 16, ten of them recurring.

[2026-08-03] DECISION: A failed calendar read raises `CalendarReadError` instead of returning an empty list, and `calendar-sync` skips the run rather than syncing nothing. | REASONING: `syncToFirestore` deletes every document a read does not return, so a silently-empty read would wipe the mirror and present the week as clear — the same failure we were fixing, but worse. A process holding only write-only EventKit access sees one calendar and reports no error, so that state had to become loud. Observed live: the 15:26 launchd tick hit `EKAuthorizationStatus 4`, aborted, and preserved the mirror. | CONTEXT: Stale is recoverable; silently blank is not.

[2026-08-03] DECISION: The read window starts at local midnight, and `days_ahead` counts today (1 = today, 2 = today and tomorrow). The window read is reported back to the caller. | REASONING: The old window started at `current date`, so a 9am meeting vanished from "today" at 9:01 and an all-day event today — start time local midnight — was never returned at all. Reporting the window means a model answering "is tomorrow clear?" can check coverage instead of assuming it. | CONTEXT: Same investigation. All-day events also now carry an `allDay` flag through to the briefing, so they render as "all day" rather than 12:00 AM–11:59 PM and no longer trip the ≤9am early-meeting alert.

[2026-08-03] DECISION: Kept the hand-maintained `READ_CALENDARS` allowlist rather than deriving it from `DisabledCalendars` now that EventKit exposes `calendarIdentifier`. | REASONING: The allowlist was originally a workaround for not being able to resolve those UUIDs, and that constraint is gone — but "unchecked in Calendar.app" is not the distinction that matters. Birthdays, Siri Suggestions, Scheduled Reminders and three redundant US holiday calendars are all enabled and all noise in a briefing. The list is editorial, so it stays explicit; unmatched names are now reported as `missingCalendars` instead of being skipped silently. | CONTEXT: A renamed calendar previously dropped its entire contents with no signal.

It lives in the GitHub secret FINNHUB_API_KEY. Without the key, the headlines still run and the markets strip is not shown.

[2026-10-06] DECISION: MAISIE becomes Jack's CRM and address book, with contacts, companies and notes stored in Firestore (`contacts`, `companies`, `contactNotes`). It holds the only copy of CRM data, and there is no two-way sync with Apple Contacts or Outlook. | REASONING: Two-way sync is where most of the risk and effort would be, and Jack's goals (look up contacts, keep notes, later link emails and meetings) do not need it. The six tools live in `functions/src/tools/contacts.ts`, so the web chat and the `maisie` MCP server share one implementation. Email address is the identity key: creating a second contact with an address already on file is refused, both by the tools and by the web page. The company name is looked up from `companyId` when read rather than copied onto each contact, so renaming a company changes it everywhere. Search filters in memory, which is adequate for hundreds of contacts. | CONTEXT: Phase 1 of 4. Next: links from contacts to emails (Message-ID), calendar events and URLs; then a one-way import from Apple Contacts; then automatic linking. The MCP server stays local over stdio; using it from claude.ai or a phone would need a remote HTTP MCP server with proper authentication.

[2026-10-06] DECISION: CRM Phase 2 — contacts and companies can be linked to emails, meetings and web pages, stored in a new `contactLinks` collection. Each link keeps its own copy of the item's details (title, date, sender or calendar, join link) instead of pointing at another record. | REASONING: The calendar mirror deletes events once they pass, and Mail can only be reached from Jack's Mac, so a link that pointed at either would break. An email keeps its Message-ID, which does not change, and the page opens it in Apple Mail through the `message://` scheme. A meeting keeps its Apple Calendar uid, and the desktop `calendar_read` now returns it. Only http and https addresses are stored or opened, so a link cannot run script. The same email, the same web page, or the same meeting on the same day cannot be linked twice to one record. | CONTEXT: Two new tools, `link_to_contact` and `remove_contact_link`, are available in the chat and over MCP. On the web page, web pages and meetings can be added by hand; emails are added through MAISIE because they need the Message-ID. Deleting a contact also deletes its links. Phase 3 is a one-way import from Apple Contacts.

[2026-10-06] DECISION: CRM Phase 3 — MAISIE imports everyone in Apple Contacts, one way, and the import only ever adds. | REASONING: Jack chose everyone over chosen groups. Apple fills blank fields and adds new email addresses and phone numbers; it never overwrites a field Jack filled in, never removes anything, and never touches notes or links, so the import is safe to run again at any time. Cards are matched by the Apple identifier saved on an earlier import, then by email, then by an exact name that only one contact has; two contacts with the same name are never guessed between. The reader runs inside the local `maisie` MCP server (and a terminal command beside it), not the desktop bridge, because only those can reach both macOS and Firestore, and the bridge is an ES module package that the server's CommonJS code cannot import. The cloud chat cannot run it. The MCP tool defaults to a dry run, so a model cannot import by leaving the flag out. | CONTEXT: The macOS read cannot run in Linux CI, so the tests feed the server a saved sample of the reader's output through MAISIE_APPLE_CONTACTS_FIXTURE; the reader script itself is untested until Jack's first run on his Mac. Firebase setup moved from server.ts to src/mcp/firebase.ts so the server and the import command share it.

[2026-10-06] DECISION: CRM Phase 4 — emails and meetings are linked to contacts automatically by a launchd job on Jack's Mac every 15 minutes. Emails: received and sent, every Mail account. Meetings: Jax and IHRDC calendars only, once started. The first run looks back 30 days. | REASONING: Jack chose received and sent emails, 30 days of history, work calendars only and a 15-minute interval. Mail is reachable only on the Mac, so the job runs there, as the Apple Contacts import does; the linking rules sit in functions/src/tools/contact-autolink.ts so they are tested against the emulator. Items with more than 15 other people are skipped, because an all-hands meeting or a mailing says little about any one contact. Jack's own addresses come from his Mail accounts, so nobody has to keep a list. Automatic links get a fixed id from the contact and the item, which makes repeat runs harmless, and removing one records a dismissal under the same id so it stays removed. | CONTEXT: The dry run on 2026-10-06 found 57 meeting links and 313 email links over 30 days. get_contact now reads the 100 newest dated links plus every web page, because automatic links can give a busy contact hundreds; that needs the two new contactLinks indexes on (contactId, date) and (companyId, date).
